# 0009. Scaffolding, sync and watch only ever add, and never surprise

- Status: Accepted
- Date: 2026-09-21

## Context

Three features write to the workspace on their own initiative: `qw new` (creates a project),
`qw sync` (clones the registry's repositories) and `qw watch` (re-runs a project when a file
is saved). Each can do harm if it is too eager: a generator that overwrites a folder, a clone
that replaces work in progress, a watcher that re-runs itself in an endless loop because a run
writes files inside the folder it watches.

## Decision

1. **Creation refuses to overwrite.** `qw new` stops if the slug is taken or the folder exists.
   `qw sync` never touches a folder that is already there (a folder named like a registry entry
   counts as *present*, whatever it contains) and the git adapter independently refuses to clone
   into a non-empty directory. Two guards, in two layers, for the operation that could lose work.
2. **The template is data, and what it generates must pass the doctor.** The project template
   lives in `data/templates/project/`, rendered with Jinja2 in `StrictUndefined` mode (a missing
   variable is an error, not an empty string in a generated file). Files whose braces belong to
   the *generated* program (CSS in the dashboard) are copied verbatim instead of rendered.
   The tests generate a project, build its environment, run it and require a clean doctor
   report (including the determinism check): a generator whose output fails the workbench's own
   rules is a bug.
3. **Sync clones over HTTPS only, by default.** Public repositories need no credentials, and it
   rules out exotic transports a registry entry could otherwise name. The trusted prefixes are a
   constructor argument so tests can use local bare repositories; the URL is passed after `--`
   so it can never be read as a git option. One failing clone never stops the others.
4. **Watch ignores what a run produces.** Only `.py` files under `src/` and the config folders
   count, and `outputs/`, `venv/`, `__pycache__/`, `.git/`, `.certs/` and `data/` are excluded
   *before* debouncing. Otherwise the `__pycache__` written by every run would trigger the next
   one. Runs never overlap: edits made during a run are kept and cause exactly one more run.
   Watching starts before the first run so an edit made during it is not lost.

## Consequences

- Running `qw sync` or `qw new` is always safe; the worst outcome is a message saying why
  nothing was done.
- A project generated by `qw new` follows the portfolio's conventions without the user having
  to remember them, and the workbench can edit its configuration form immediately (every
  constant has its explanatory comment).
- Changing the template is a change to data files, and the tests notice if it stops passing the
  doctor.
- Watch mode is CLI-only for now; the GUI's run buttons cover the interactive case.

## Alternatives considered

- **Cookiecutter / copier**: another dependency and another template language for nine small
  files; Jinja2 alone is enough.
- **Update existing clones on sync (`git pull`)**: convenient, but it can conflict with local
  edits. The workbench's stance is that it does not change git history behind the user's back
  (see ADR 0008); the Git panel and plain `git pull` remain available.
- **Polling instead of OS notifications for watch**: portable but wasteful and slower to react;
  `watchdog` uses the operating system's own change events.
